# 資安說明

本文件說明這個網站的資安設計、每一類威脅的對應防護、驗證方式，以及**程式無法解決、必須靠人員流程處理**的部分。

> **關於「完全沒有漏洞」**：沒有任何系統可以被保證絕對安全。這份專案的做法是：逐項對照常見攻擊類型，實作防護，並用自動化測試證明防護有效（包含「故意拿掉防護，測試就會失敗」的對照實驗）。下方也誠實列出殘餘風險。

---

## 1. 架構與信任邊界

```
 訪客瀏覽器 ──(公開 GET，唯讀)──▶ Apps Script 後端 ──▶ Google 試算表（內容）／Drive（圖片）
 管理員瀏覽器 ─(POST + Google ID token)─▶ Apps Script 後端（驗證 token、檢查管理員名單、才寫入）
```

- **沒有資料庫、沒有伺服器**：沒有 SQL，也沒有可被入侵的主機。
- **前端不可信**：按鈕的隱藏只是介面，**所有權限檢查都在後端**。
- **後端不信任前端傳來的任何東西**：每個欄位都有型別、長度、格式驗證，並用白名單限制可寫入的欄位。
- **不依賴 Cookie**：登入憑證（Google ID token）只放在記憶體，每次請求放在 body 裡。

## 2. 威脅對照表

| 威脅類別 | 本專案的防護 | 怎麼驗證 |
|---|---|---|
| **SQL Injection** | 完全沒有 SQL。資料存在 Google 試算表，以 JSON 儲存；集合名稱、欄位都用白名單。`' OR 1=1 --`、`DROP TABLE` 等字串只會被當成普通文字。同類的「試算表公式注入」另有防護（見下）。 | `test-backend`：注入字串被當純文字儲存；危險集合名稱被拒絕 |
| **XSS（Cross-Site Scripting）** | ① 所有輸出一律經過 `escapeHtml` 或 `textContent`；② 圖片網址只接受 `lh3.googleusercontent.com/d/<id>`，`javascript:` 一律拒絕；③ `mailto:` 連結先驗證格式；④ 嚴格 CSP：禁止行內腳本、行內樣式、`eval`；⑤ 沒有行內事件屬性 | `test-frontend-xss`：惡意資料灌進每個欄位，沒有任何腳本被執行。**移除 CSP 後仍然安全**（證明不是只靠 CSP）。對照組：故意拿掉一處編碼，測試立刻失敗 |
| **CSRF（Cross-Site Request Forgery）** | 後端**不使用 Cookie 或瀏覽器自動帶入的憑證**；每個寫入請求都必須在 body 附上有效的 Google ID token，攻擊者的網站拿不到這個 token。請求一律 `credentials: 'omit'` | `security-scan`：沒有使用 Cookie／sessionStorage；`test-backend`：無 token、假 token 全被拒絕 |
| **Authentication（驗證）** | Google ID token 驗證：格式 → `aud`（必須是本站的 Client ID）→ 過期時間 → 向 Google 驗證簽章 → `iss`、`email_verified`。失敗的 token 短暫負快取；全站每分鐘最多向 Google 驗證 90 次（防耗盡配額） | `test-backend`：格式錯誤、aud 不符、過期、偽造、未驗證 Email、issuer 不對 —— 全被拒絕，且**不會消耗 Google 配額** |
| **Access Control（存取控制）** | 每個寫入動作都在後端檢查管理員名單；**先檢查身分、再限速、最後才取得鎖**（非管理員無法佔住鎖造成癱瘓）；不能移除自己、至少保留一位管理員、管理員上限 20 人；`__proto__`、`constructor` 等集合名稱被拒絕，多餘欄位不會被儲存 | `test-backend`：非管理員 8 種操作全被拒；不取得鎖；原型汙染無效 |
| **Configuration & Architectural Weaknesses（設定與架構）** | 嚴格 CSP（`default-src 'none'`、`object-src 'none'`、`base-uri 'none'`、`form-action 'none'`）；防嵌入（clickjacking）腳本；`Referrer-Policy: no-referrer`；後端只暴露 `doGet`／`doPost`／唯讀的 `getPublicDataForPage`（其餘函式名稱以 `_` 結尾，瀏覽器無法呼叫）；明確宣告最小 OAuth 權限範圍；設定值格式不對時不會對任意網址發出請求；密鑰只放在腳本屬性，程式碼與設定檔沒有任何密鑰 | `security-scan`（含密鑰掃描、函式暴露檢查、CSP 檢查）；`test-builds` |
| **Human & Procedural Weaknesses（人員與流程）** | 程式能做的：稽核紀錄（誰在何時改了什麼）、管理員異動通知信、刪除前確認視窗、管理員人數上限。其餘需靠**第 3 節的流程規範** | `test-backend`：稽核紀錄、通知信 |
| **Software & Code Flaws（程式缺陷）** | 沒有第三方函式庫（唯一的外部腳本是 Google 登入）；沒有 `eval`／`document.write`；所有輸入驗證型別、長度、格式；JSON 解析有例外處理；回應大小有上限；內部錯誤只回傳通用訊息，不洩漏細節；寫入加鎖避免競態 | `security-scan`；`test-backend`（型別錯誤、超長、錯誤訊息過濾） |
| **試算表公式注入（類似 SQL 注入）** | 管理員 Email 必須以英數字開頭（拒絕 `=`、`+`、`-`、`@`）；姓名等文字若以公式字元開頭，會加上單引號中和；內容以 JSON 儲存（以 `{` 或 `[` 開頭，不會被當公式） | `test-backend`：`=1+1@a.com`、`+1@a.com`、`=HYPERLINK(...)` 全被擋下／中和 |
| **檔案上傳** | 只接受 PNG／JPEG；檢查檔頭位元組（偽裝成圖片的 HTML、PHP 被拒絕）；**拒絕 SVG**（可夾帶腳本）；base64 嚴格驗證；大小上限；檔名清理；圖片放進專用資料夾 | `test-backend`：SVG、偽裝檔、非法 base64、超大檔案全被拒 |
| **阻斷服務（DoS）／資源耗盡** | 每位管理員每分鐘最多 30 次寫入；請求大小上限；項目數量上限；Google 驗證次數上限；公開資料快取 60 秒 | `test-backend` |
| **點擊劫持（Clickjacking）** | `theme-init.js` 偵測被嵌入時隱藏頁面並嘗試跳出（靜態主機無法設定 `X-Frame-Options`）；Apps Script 後端不使用 `ALLOWALL` | `security-scan` |
| **敏感資訊外洩** | 公開 API 不含任何管理員資訊；登入 token 只在記憶體，不寫入 localStorage；錯誤訊息過濾；程式碼無密鑰 | `security-scan`、`test-backend` |
| **供應鏈風險** | 沒有 npm／CDN 相依；Google 登入腳本只在正式模式動態載入，且 CSP 只允許 `accounts.google.com/gsi/` | `security-scan`、`test-builds`（單機版零網路請求） |

## 3. 人員與流程規範（程式無法代勞的部分）

資安事件大多出在「人」。請務必遵守：

**帳號**
1. **所有管理員的 Google 帳號都啟用兩步驟驗證**（2-Step Verification）。這是最重要的一項：管理員帳號被盜，等於整個網站被接管。
2. **不要共用帳號**；每位管理員用自己的 Google 帳號登入，這樣稽核紀錄才有意義。
3. 管理員越少越好（最小權限）。只有真的需要編輯內容的人才加入。
4. **成員離隊、畢業或換職務，當天就從管理員名單移除。**

**日常維運**
5. 每個月檢視一次試算表的 `AuditLog`（誰在何時改了什麼）和 `Admins` 名單，有不認識的紀錄就立刻處理。
6. 在 Apps Script 腳本屬性設定 `NOTIFY_EMAIL`，管理員有異動時會寄信通知你。
7. 試算表與 Apps Script 專案**只分享給必要的人**，且用「檢視者」而不是「編輯者」。
8. 上傳照片前確認：**所有人都看得到**。不要放未成年者可辨識的個資、學生證件、內部文件；成員 Email 也會公開，建議用團隊信箱。
9. 不要把 ID token、Apps Script 部署網址以外的任何憑證貼到公開場合（網站設定檔裡的 Client ID 與 API 網址本來就是公開資訊，沒關係）。

**發佈前**
10. 執行 `bash tools/run-all-checks.sh`，全部通過再發佈。
11. 確認正式版 `config.js` 的 `MODE` 是 `"api"`（不是 `"demo"`）。
12. 試算表啟用**版本記錄**（預設就有），出問題時可以還原。

**發生疑似入侵時**
1. 立刻在 Apps Script 停用部署（管理部署作業 → 封存）。
2. 檢視 `AuditLog`，確認被改了什麼；用試算表的「版本記錄」還原。
3. 移除可疑的管理員，並請所有管理員更改 Google 密碼。
4. 在 Google Cloud 重新建立 OAuth Client ID，更新腳本屬性與 `config.js`，再重新部署。

## 4. 殘餘風險（誠實說明）

| 風險 | 說明 | 建議 |
|---|---|---|
| Google 登入的一段行內樣式 | Google 登入腳本會套用一小段固定的行內樣式，我們只用「雜湊值」放行這一段（不是放寬成 `unsafe-inline`），其他行內樣式一律禁止 | 若 Google 日後更改該樣式，登入按鈕外觀可能略有差異，但不影響安全與功能 |
| CSP 靠 `<meta>` 設定 | GitHub Pages 無法設定 HTTP 標頭，因此 `frame-ancestors`、`X-Content-Type-Options`、HSTS 無法由本專案設定（HSTS 由 GitHub 提供）。XSS 防護的主力是輸出編碼，CSP 是第二道防線 | 若學校網站可放在能設定標頭的主機，可套用 `README.md` 中的標頭 |
| Token 在有效期內可重送 | Google ID token 約 1 小時內有效；若被竊取，期間內可被重複使用 | 靠 CSP + 不寫入儲存空間降低被竊風險；管理員用完後登出並關閉分頁 |
| Apps Script 無法依 IP 限流 | 平台限制，只能做全站與每位管理員的限流 | 若遭大量濫用，可暫時封存部署 |
| Google 帳號被盜 | 這是最大的風險，程式無法防範 | 兩步驟驗證（第 3 節第 1 點） |
| 公開內容一律是公開的 | 網站內容、成員 Email、照片都是任何人可讀 | 不要放敏感內容 |
| 單機版的「管理員登入」不是安全邊界 | 單機版是展示用，資料只在自己的電腦，沒有真正的登入驗證 | 不要把單機版當成正式網站對外提供 |
| 平台本身的漏洞 | Google／GitHub／瀏覽器本身的漏洞不在本專案範圍 | 保持瀏覽器更新 |

## 5. 如何自行驗證

```bash
bash tools/run-all-checks.sh        # 一次跑完全部
node tools/test-backend.mjs         # 後端：模擬 Apps Script，嘗試 59 種攻擊與錯誤情境
node tools/test-frontend-xss.mjs    # 前端：用惡意資料測 XSS（有／無 CSP 各一次）
node tools/security-scan.mjs        # 靜態掃描：危險寫法、CSP、密鑰、函式暴露
node tools/test-builds.mjs          # 三個交付版本實機測試
```

測試本身也有被驗證過：把防護拿掉（例如舊版後端、少一處 `escapeHtml`、有問題的 HTML），測試都會**失敗**，代表測試真的抓得到問題。
